## P1 — CONFIRMED, minor, with a narrower owner and impact

**Attempted disproof: wrong entrypoint.** `family-run/summarize.py` is a post-execution reporter, not an independently advertised cryptographic verifier. Its actual caller is `family-run/run.py:118–122`; the runner verifies inputs/scripts/pins before execution and again afterward (`62–81`, `106–117`). `FamilyDriver.java:48–57` checks closure/request/freeze/ledger/JDK bindings and `78–101` creates receipts around the actual evaluation and verifies the closure afterward. The summary explicitly describes observations as discovery evidence pending independent review (`summarize.py:83,120`). These are meaningful counterexamples to treating `complete` as an independent evaluator attestation.

**Attempted disproof: failure-to-verdict confusion.** Five synthetic controls failed closed: nonzero evaluation exit, timeout process status despite all retained records, missing output receipt, missing raw record, and wrong raw-record ID. All returned `failed_or_incomplete`. The missing-record case explicitly retains an unobserved request, null record and unknown verdict explanation; it does not manufacture a rejection. Thus the tested defect is provenance consistency, not demonstrated conversion of process failures into invoice verdicts.

**Evidence that survives.** `summarize.py:23–28` checks only selected receipt fields; `50–59` trusts selected metadata fields and does not reconcile argv/digests. Sixteen fresh synthetic cases used byte-identical copies of `summarize.py` and `common.py`, with the copy's normal OUT pointing to its own directory. No evaluator or runner executed. Ten *individual* contradictions still returned `True`, `status=complete`, zero contract errors:

- Output receipt: wrong ID, ordinal 999, or `evaluate_returned=false`.
- Input receipt: wrong closure, driver, freeze, or ledger SHA-256.
- Evaluation metadata: impossible argv, wrong stdout digest, or wrong stderr digest.

The unchanged control returned complete; the five failure controls above returned incomplete. All ten provenance-fault cases preserved finding-occurrence bytes exactly. The fault was injected into the first DEVELOPMENT mutation (`F01-prefix-b`), not a held-out case. Each directory contains an explicit SYNTHETIC declaration, before/after mutation hashes, exact copied sources and generated reports. See `adversarial-provenance/summary-results.json`, `probe.py`, and `summary-*/SYNTHETIC.json`.

**Independent counterevidence about current originals.** A fresh read-only audit checks all 60 original input/output receipts, raw identities, the ordered stdout/raw binding, exact collateral finding occurrences, evaluation command/binding/metadata agreement, actual stream digests and closure/driver/freeze/ledger bindings. These pass. Together with discriminant checks below, 214 assertions pass in `adversarial-provenance/original-bindings.json`. This supplements the supplied replay evidence without re-executing evaluations.

**Decision and minimal correction.** Keep minor only as a future publication gate consistency requirement. The AC requires exact provenance, so accepting mutually contradictory receipts or metadata is material if this reporter is reused as that gate. Put the missing comparisons in the future independent verifier before it declares provenance complete; it need not turn the frozen historical summarizer into a standalone verifier. Reconcile output ID/ordinal/returned flag and input identity/provenance fields with the same verified request, closure, driver, freeze and ledger bytes; reconcile evaluation argv and raw stream digests across declaration/binding/command/metadata. This does not require packing/publication design or acceptance-count assertions. Do not rewrite historical receipts/scripts.

**Residual limits.** Synthetic mutations bypass the normal producer and invalidate the immutable outer manifest. They prove missing internal consistency checks, not a naturally occurring failure in the original run or an attacker-authenticity bypass. A trusted manifest would reject those mutations. Merely comparing self-reported hashes cannot authenticate an evaluator. There is no evidence here that current invoice records or collateral findings are wrong.

## P2 — CONFIRMED, minor, restricted to launch-error accounting

**Attempted disproof: deliberate fail-fast behavior and no lost child output.** `discriminant/run_v2.py:23` writes the command before launch. An uncaught launch OSError aborts the caller before record parsing (`76–86`); `finally:92–94` still attempts to retain the accumulated prior outcomes. It does not invent an invoice verdict or silently return success. For a nonexistent executable, no child started, so no emitted stdout/stderr bytes were lost. The retained command also gives forensic evidence of the attempted launch. Those facts rule out a stronger claim that the entire attempt disappears or that this branch disguises failure as an invoice result.

**Evidence that survives.** Extracted and compiled the exact `execute` helper AST at `run_v2.py:22–36`, preserving source/AST hashes and line spans. Supplied only synthetic globals pointing to an owned directory and the actual subprocess module. Extracted its exact write helper from `discriminant/prepare.py:14`. An actual bounded nonexistent-binary call propagated `FileNotFoundError`; only `.command.json` existed, with no metadata/stream files and an empty outcomes list. Nothing was monkeypatched into a real oracle.

Two counterexample probes with the same helper launched short synthetic Python processes. Exit 7 retained both nonempty streams, metadata and outcome; timeout retained both partial streams and an explicit timeout outcome before re-raising. The corresponding three probes against the exact family-run `execute` AST (`run.py:45–61`) retained all four files and one explicit outcome in every case. Its nonexistent-binary result was `status=launch_error`, null exit code, exception detail and empty stream hashes, followed by an unsuccessful-process exception. See `adversarial-provenance/helper-results.json` and each `helper-*/SYNTHETIC.json`/`probe-result.json`.

The independent original audit also verified command/metadata/actual-stream hash agreement for all eight discriminant evaluation attempts: four first-attempt exit-1 failures and four corrected exit-0 completions. None is a historical launch-error example. No discriminant was reevaluated.

**Decision and minimal correction.** The explicit AC that all attempts be preserved makes a command with no machine-readable outcome an accounting gap in a future reproducer, even though failing fast is legitimate. Record `launch_error`, null exit code, exception detail, argv/cwd and empty stream files/digests on process-start OSError; append the outcome before propagating failure or entering the runner's normal failure policy. Preserve earlier outcomes and partial streams, and distinguish requested work never attempted from a failed launch. Continuing after failure is not required by this finding. The existing family helper demonstrates the local record shape; no broad exception swallowing or changes to frozen helpers are necessary.

**Residual limits.** Probed only a real FileNotFoundError, a nonzero child and a timeout; not every OSError subtype, interruption or disk-write failure. The helper was isolated rather than executing full main, so caller/finally conclusions are from cited source inspection. This is bookkeeping hardening for future reproduction, not evidence of missing historical launches or invalid labels.
